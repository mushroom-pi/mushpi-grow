## Startup Sequence (`main.py`)

1. `IO()` — initialises GPIO, turns onboard LED ON.
2. `DHTReader()` — initialises DHT11 sensor.
3. `load_config()` — reads `config.json` with shallow merge over defaults. Returns `(cfg, load_errors)` — catches malformed JSON and non-object top-level gracefully.
4. `validate_config(cfg)` — validates all fields (device_name, api_port, hub_url, wifi, control, pins, reboot) for type and range correctness, and rejects duplicate GPIO assignments: no two roles may share a pin in the **effective** `pins` map (config.json merged over defaults by `load_config()` — `_append_duplicate_gpio_errors`). Accumulates all errors. If any errors (load or validation): prints them to serial, then enters terminal `error_blink_blocking()` state (3 fast blinks + pause forever). Device does NOT start WiFi, control loop, or server.
5. **Apply persisted GPIO mapping** — reads `pins` and `active_high` from `cfg`, applies them to `state.devices`, then calls `sensor.__init__()` and `io.__init__()` to re-initialise GPIO on the persisted pin assignments and polarity. Runs after validation so bad persisted data can't crash re-init; the prior default-constructed `io`/`sensor` instances are briefly double-inited (harmless — relays are OFF).
6. `init_uptime()` — reads `uptime.json` sentinel first: if `pending_type` is set ("scheduled"/"soft"/"hard"), that's the reboot reason (preserving cumulative for scheduled/soft, resetting for hard). Falls back to `machine.reset_cause()` only when no sentinel exists (unexpected reboots: WDT → "watchdog", PWRON → "power_on"). Writes fresh `uptime.json` to flash.
7. `state.init_system_info(cfg)` — caches board/MicroPython/build metadata.
8. `state.check_mdns_firmware(cfg["device_name"])` — warns if firmware < v1.26.0 (mDNS won't work; see README).
9. **Force-provision check** — reads GP0 (internal pull-up). If LOW, sets `_force_provision = True`. Also sets `_force_provision = True` when `wifi.ssid` is empty (fresh-device first boot — the normal path into AP mode).
10. `connect_wifi()` — tries each candidate network (primary + `networks` list), up to `retries` per SSID; LED stays OFF until connected, then LED ON. Returns `(wlan, ip)`.
11. **Offline (AP) mode decision**: if `_force_provision` OR `ip is None`:
    - `start_ap_provisioning(cfg)` — open AP at `192.168.4.1` (thin wrapper over `ensure_ap_up()`, the one AP-setup code path shared with the watchdog's runtime bring-up)
    - `io.start_provisioning_blink()` — slow double-blink LED pattern
    - `main()` spawns `control_loop(..., sensor_fault_cut=True)` — passed the single shared `wdt` armed before the mode branch (see the WDT bullet in step 12) — before `await start_server(mode="ap")`; the unit **regulates offline** (see §Offline (AP) operating mode). Still no announce, no `reboot_scheduler_loop`, no `wifi_watchdog_loop`, no NTP.
12. **STA mode** (normal boot):
    - `state.attach_wlan_info(wlan, cfg)` — caches MAC, IP, hostname, port.
    - **Hub DNS pre-resolution** — at `main.py` **module scope** (STA branch, right after `connect_wifi()` returns and before `asyncio.run(main())`), `announce.presolve_boot_hub(cfg, wlan)` resolves the hub host once and caches it in the module-level `announce._hub` dict. This is the sanctioned blocking boot path — the same slot `connect_wifi()` occupies: nothing is scheduled yet and the `WDT` does not exist yet, so a slow `socket.getaddrinfo()` — which has no timeout of its own — cannot starve or reset anything. It is best-effort: it prints, never raises, skips when `hub_url` is empty, and skips when the link or IP is missing. A dotted-decimal hub host is used directly with no lookup at all. **This is the only name resolution the announce path ever performs** — the NTP sync in `app/reboot_scheduler.py` resolves `reboot.ntp_host` on its own, from a task (see §MicroPython quirks).
    - **WDT (Watchdog Timer)**: armed **once** — `main()` constructs `WDT(timeout=8000)` after `start_metrics()` and **before the mode branch**, and passes the same `wdt=` to `control_loop()` in both the STA and the offline branch (offline units are not exempt: they run the control loop and are protected like STA). Construction sits after every blocking boot operation, which all ran at module scope before `main()`: `connect_wifi()`, `presolve_boot_hub()` (STA), `start_ap_provisioning()` (AP), `runtime_state.restore()`. The rp2 watchdog cannot be stopped once armed, so nothing may block between construction and `control_loop()`'s first feed — boot WiFi (30 s+) must stay behind it or it triggers a spurious reboot. Fed from `control_loop`'s 200 ms chunked-sleep loop — covers event-loop-wide blocking hangs and control_loop task death. Not fed from an independent task (would miss control_loop death). The boot pre-resolution above is what keeps the boot slot's unbounded call (`getaddrinfo()`) out of the armed window; the announce transport bounds everything else, and the NTP sync's own lookup is the one known exposure inside the window (see §Announce transport & watchdog budgets).
    - `main()` async task (`start_metrics()` runs first, before the mode branch — it launches the background event-loop utilisation meter; then these tasks are created **in this order**, and `await start_server()` runs last):
      - Spawns `reboot_scheduler_loop()` — the **NTP sync runs from this task**, not the boot path: up to 3 attempts spaced 30 s at startup, then every 5 min via `_NTP_RETRY_MS` until one lands; then polls every 60 s and triggers `machine.soft_reset()` at the configured hour/minute (disabled by default). Not spawned offline. **Note:** its sync performs a blocking name **resolution** of `reboot.ntp_host` itself — see §Announce transport & watchdog budgets, and the time-semantics bullets in §MicroPython quirks.
      - Spawns `announce_then_retry_once(cfg, wlan, io, stop_event=...)` — tries POST to hub; on failure, retries **forever** on the `_RETRY_BACKOFF_S` schedule (30, 30, 60, 120, 300 s, capped at 300 s thereafter) until an attempt succeeds or `stop_event` fires. `main.py` is its **only** spawner.
      - Spawns `control_loop(cfg, wlan, io, sensor, stop_event=..., wdt=wdt)` — hysteresis loop; the **only** watchdog feed site, every 200 ms inside its chunked-sleep loop. If the loop hangs or dies, the WDT expires → hard reboot → WiFi reconnects + re-announces.
      - Spawns `wifi_watchdog_loop()` — monitors link health; on drop, brings the offline AP up (`ensure_ap_up(cfg)`) and shows the offline double-blink, reconnects with backoff (5/10/30/60 s, then caps at 60 s — `_BACKOFF_MS`); on link-up, drops the AP again (`ap_down()`), refreshes cached WLAN info, re-arms the LED heartbeat, and logs — it does **not** re-resolve the hub or spawn an announce (see §Wi-Fi watchdog).
      - **Announce internals**: `announce_then_retry_once()` wraps the coroutine `_post_once_async()` (one POST per attempt, body built by `payload()`) over a hand-rolled `usocket` transport — the old `announce_once_blocking()` helper and the module's `urequests` import are **removed**. Every phase boundary is followed by an `await asyncio.sleep_ms(0)`, so an unreachable hub no longer starves `control_loop()` or the HTTP server. The per-attempt budgets are **3 s connect / 1 s per send·recv slice / 6 s response-header read**, all **firmware constants at module level in `app/announce.py`, not `config.json` keys** — an operator must not be able to dial a blocking announce that starves the control loop. The POST target is resolved by `announce_url()` applied to the configured address, which appends `_ANNOUNCE_PATH` instead of using the value verbatim. Resolution is cached in `announce._hub` (`{"target", "addr"}`, mutated in place) by `_ensure_resolved()`; its only public entry point is `presolve_boot_hub(cfg, wlan)` (boot, best-effort), and the retry path reads the cache but **never resolves**. Only the response status line is parsed — the body is never read, as before — and each attempt prints one line, `announce: attempt N done in <ms> ms (status <code>)`, which is the bench-recordable trace.
      - **`announce_then_retry_once` is re-entrant**: the coroutine itself is safe to call again, but nothing does at runtime any more — the boot task is the only one, and it ends once an attempt is acknowledged (otherwise it backs off forever). If a runtime re-announce is ever reintroduced, its caller must cancel any prior announce task first to avoid overlapping heartbeat/LED control.
      - `await start_server()` — Microdot HTTP server on `0.0.0.0:<api_port>`. Awaited, not spawned, so it is the task that keeps `main()` alive.
13. **Runtime-state rehydrate** — after the AP/STA branch, at module scope, before `asyncio.run(main())`: `runtime_state.restore(cfg, io)` reads `runtime.json` and applies persisted grower state. Runs before the WDT is created and before any task in step 12 exists, so `control_loop()` starts with the loop flag and its relay latch already primed. Order inside is load-bearing: setpoints written **in place** into `state.setpoints`; loop flag + `control_loop`'s first-pass latch primed via `control.prime_control_enabled()`; **loop off (STA and offline, alike — the former AP skip is removed)** → `io.heat_off()` unconditionally first, then stored fan/humidifier positions through the `IO` helpers; **loop on** → no relay touched. Bad or absent file boots to the `state.py` defaults (25 / 60, loop on, outputs off) — `_load()` never raises, and restored values are **not** fed into `validate_config()`. See §Persistence for the file.

## Firmware Requirements (mDNS)

For `<device_name>.local` mDNS resolution (so the hub or a browser can reach the unit at `http://<device_name>.local:5000` without knowing its IP), the Pico must run **MicroPython ≥ v1.26.0** (v1.25.0 stable also contains the fix, but v1.26.0 is the recommended minimum and confirmed working). Pre-release/preview builds of v1.25.0 do **not** have the fix. AP-mode mDNS is unsupported ([#10957](https://github.com/micropython/micropython/issues/10957)). mDNS is link-local — only resolves on the same subnet; cross-subnet needs a router mDNS reflector.

The rp2/CYW43 mDNS responder was half-wired for years: `mdns_resp_init()` opened UDP/5353 but the driver never called `mdns_resp_add_netif()`, so no announcement packets were sent. Fixed in v1.25.0 stable by [PR #17057](https://github.com/micropython/micropython/pull/17057). `app/wifi.py` uses `network.hostname(name)` before `active(True)` (the modern API; `wlan.config(hostname=...)` is deprecated). `state.check_mdns_firmware()` warns at boot if the firmware is too old.

## Hardware Pins (defaults)

| Device           | GPIO | Notes                                                       |
|------------------|------|-------------------------------------------------------------|
| Force-provision  | 0    | Internal pull-up; hold LOW at boot to force AP mode         |
| DHT11            | 4    | Temperature + humidity sensor                               |
| Humidifier relay | 6    | Active-low by default                                       |
| Fan relay        | 7    | Active-low by default                                       |
| Heater relay     | 8    | Active-low by default                                       |
| Onboard LED      | `LED`| Status indicator                                            |

- `active_high` in `config.json` flips relay polarity. The `IO` class in `app/hw.py` handles this automatically — never toggle GPIO directly.
- Pins can be remapped at runtime via `POST /setup` in **either operating mode** (STA and offline AP) and are persisted to `config.json` (`pins`, `active_high` keys), surviving reboot. Only GPIOs **1–22, 26, 27, 28** are assignable — GP0 is the force-provision jumper, GP23–25 and GP29 are reserved for the CYW43439 wireless chip (named refusal reasons; see §Unit page for the constants). A change that would leave two functions on one GPIO (after merging the partial update with the current mapping) is rejected with `400` before any remap or config write; the endpoint finally runs the boot rule itself (`_append_duplicate_gpio_errors`) over that merged map too, so a mapping it accepts is by construction one the unit would boot with.
- The **boot** duplicate rule (`validate_config()` / `_append_duplicate_gpio_errors`) is separate and stricter than the `POST /setup` merged-view rule: any two roles sharing a GPIO in the effective (default-merged) `pins` map is fatal, with no partial-update allowances — there is no live mapping at boot to merge against. Do not "unify" the two rule sets; the setup rule's allowances (same-pin re-assign, within-request pin swap) must stay. The setup rule is semantics-locked across firmware, `mushpi-mock` and the server's setup proxy; the boot rule exists in the firmware only. Running `_append_duplicate_gpio_errors` inside `POST /setup` over the request-merged map is an **endpoint-internal guarantee**, not a unification and not a cross-repo contract change — the boot rule still guards `config.json` at boot, terminal and firmware-only, and the merged-view allowances are unchanged.

## Control Loop Logic

Runs as a `uasyncio` coroutine every `control.period_s` seconds (default 10 s in `config_loader.py`; matches the checked-in `config.json`).

- **Humidifier**: ON when `humidity <= target − humidity_deadband` (asymmetric low-side deadband). Stays ON until humidity rises above the deadband threshold.
- **Fan**: ON when `humidity > target + hyst_hum` (high-side deadband). Stays ON until humidity drops to `<= target + hyst_hum`.
- **Deadband**: between `target − humidity_deadband` and `target + hyst_hum` neither humidifier nor fan runs — prevents fighting between the two actuators. The deadband is asymmetric: the low-side gap (`humidity_deadband`, default 3) and high-side gap (`hyst_hum`, default 5) are independently configurable.
- **Heater**: ON when `temperature <= target − temperature_deadband` (asymmetric low-side deadband, default 1).
- **Minimum runtime**: once a relay turns ON, it stays ON for at least `min_runtime` seconds (default 30) before it can be turned off. Tracked per-relay via `_on_since` timestamps (ticks_ms). This prevents rapid cycling of relays when readings hover near deadband boundaries.
- Humidifier and fan are **mutually exclusive** — each branch calls the other's `_turn_off()` helper as a safety measure.
- When `control_enabled = False`: keeps sampling the DHT11 every `control.period_s`, calls `relays_off()` once (relays only — LED heartbeat continues), resets `_on_since` tracking, and skips hysteresis actuation until re-enabled. Sampling is decoupled from actuation so `GET /`, `/sensors`, and `/health` keep returning fresh readings.
- API handlers (`POST /outputs`, `POST /control`) also update `_on_since` so min-runtime tracking stays consistent when relays are driven outside the control loop.
- **Offline sensor-fault output cut** — `sensor_fault_cut=True`, wired by `main.py` on the offline branch only. In the enabled branch, when `status["last_sensor_ok_at"]` is older than `_SENSOR_STALE_CUT_S` (120 s; plain `time.time()` deltas — valid offline, the RTC ticks without NTP), the loop **holds the cut every iteration**: `io.relays_off()` + `reset_on_since()` each pass, no `evaluate_hysteresis()` call, and the module-level `_sensor_fault_hold` latch prints the transition once. The latch clears (with a print) and regulation resumes when a fresh plausible reading lands. `last_sensor_ok_at = None` (never read) is NOT "stale" — `evaluate_hysteresis`'s `None` guards already suppress actuation before the first plausible read. The per-iteration re-assert is deliberate: `POST /outputs` can energise a relay between ticks and the cut must win. `api.py`'s `POST /setpoints` immediate re-evaluation consults `control.fault_latched()` and skips actuation while the latch is set (the only other actuation site outside the loop).
  - **Wired-parameter pattern**: `sensor_fault_cut` is passed in by `main.py`; `app/control.py` never learns Wi-Fi state (module-ownership rule stands). Any future mode-gated loop behaviour follows this pattern — the caller decides the mode, the loop receives a plain parameter.
  - **`_SENSOR_STALE_CUT_S` is a firmware constant by design** — deliberately not a `config.json` key, the same philosophy as the announce budgets: an operator-tunable safety threshold invites misconfiguration.
- **`control_loop()`'s second parameter (`wlan`) is dead**: both `main()` call sites pass the active interface (`ap` offline, `wlan` on STA) and the loop never reads it — kept for call-site symmetry, flagged for later removal; new code must not start depending on it.

**Key design rule**: sensor sampling must remain independent of `control_enabled` (observability vs. actuation separation). `io.all_off()` is for fail-safe/shutdown only; use `io.relays_off()` for control-disabled state.

## Offline (AP) operating mode

The Pico enters the **offline operating mode** when **any** of these is true:

1. **No Wi-Fi configured** — `wifi.ssid` is empty (factory default; the normal way a fresh unit reaches it). `main.py` sets `_force_provision = True` and `connect_wifi()` skips the STA attempt entirely (returns `(wlan, None)` immediately).
2. **GP0 held LOW at boot** (force-provision jumper, internal pull-up).
3. **Wi-Fi connection failed** after all attempts (`connect_wifi()` retries 3× per candidate SSID).

A runtime STA link-drop is NOT a mode switch: `wifi_watchdog_loop()` keeps the unit in its boot mode and merely brings the same AP up alongside (see §Wi-Fi watchdog) so the page stays reachable — regulation never stops.

Details:

- SSID: `mushpi-provision-XXXX` (XXXX = last 4 hex of AP MAC), open network — deliberately password-free; the offline network is short-range and unit-local.
- IP: `192.168.4.1`, port `5000`. The AP stays up **indefinitely** (until credentials are provisioned or a watchdog-recovered STA link drops it again — see `ensure_ap_up()`/`ap_down()` in §Wi-Fi watchdog).
- LED: slow double-blink (200/200/200/800ms) — the unit is **working**: regulating and serving its page, but has **no usable Wi-Fi link**; regulation continues throughout, and it is not a provisioning-only or waiting state.
- **The control loop runs offline** under the same watchdog timing rules as STA (WDT armed in `main()`, `control_loop` the only feeder). Relays are NOT boot-safe-off any more; the loop regulates against the persisted/restored targets.
- Offline-only safety: the **sensor-fault output cut** (see §Control Loop Logic) — no hub is watching the readings, so stale values cut the outputs instead of driving relays.
- The unit page is the landing page offline as well: `GET /` (for HTML browsers) and `GET /ui` return the unit status page **fully operable** — offline banner, live controls, reboot card shown, targets/devices persist, the Mapping card works (see §Unit page). The Wi-Fi setup form has its own route, `GET /provision`, served in both modes; the banner's "To join a network" link points there. `GET /` answers API clients with the same JSON snapshot as in STA.
- Control POSTs (`/setpoints`, `/outputs`, `/control`) are **accepted offline** exactly as on STA (including `runtime.json` persistence), and `POST /setup` is **accepted offline** too — pin remapping is offered in both modes. The unit page posts `/setup` same-origin straight to the unit, so the hub's 422 setup-proxy pre-check never protected this path; the firmware's own validation (per-role GPIO refusals, the merged-view duplicate rule, and the boot duplicate rule run over the merged map before writing) stands alone. Recovery from a fatal `config.json` error is a physical reflash identically in both modes. `POST /provision` and `POST /reboot` keep their own semantics.
- Rejoin is **restart-based**: `POST /provision` with `{"wifi":{"ssid":"...","password":"..."}}` writes `config.json` and reboots into STA; when the router simply comes back, `POST /reboot` (or the page's reboot card) retries the join. There is no background STA rejoin task offline — `wifi_watchdog_loop()` is a STA-mode task (no link to monitor offline).
- Announce, `reboot_scheduler_loop` and the Wi-Fi watchdog do **not** run offline. No NTP: `time.time()` still ticks (the RTC runs without a sync), which is what makes the offline staleness math valid.
- CORS headers are enabled on all responses.
- mDNS does NOT resolve on the AP — use the IP directly.
- Force-provision: hold GP0 to GND during boot.

## config.json

```json
{
  "wifi": {
    "ssid": "MyNetwork",
    "password": "secret",
    "networks": [
      {"ssid": "FallbackNetwork", "password": "secret2"}
    ]
  },
  "hub_url": "http://<hub_ip>:3000",
  "hub_secret": "mushpi-dev-secret",
  "device_name": "pico-unit1",
  "api_port": 5000,
  "control": { "period_s": 10, "hyst_hum": 5, "hyst_temp": 1, "humidity_deadband": 3, "temperature_deadband": 1, "min_runtime": 30 },
  "reboot": { "enabled": false, "hour": 4, "minute": 0, "ntp_host": "pool.ntp.org", "ntp_tz_offset_hours": 0 },
  "pins": { "dht": 4, "humidifier": 6, "fan": 7, "heater": 8 },
  "active_high": false
}
```

- `device_name` must match the `handle` field in `mushpi-server`'s `PicoUnit` entity.
- `hub_url` carries the hub's **address only** — scheme, host and port (see example above). The unit appends `/v1/pico-units/announce` itself, via the `_ANNOUNCE_PATH` constant in `app/announce.py`. Surrounding whitespace and trailing slashes are tolerated, and a value that already ends in the announce path is used unchanged, so units flashed with the older full-endpoint form keep working without being re-flashed. An empty value is valid: the unit runs standalone and prints `announce: skipped (hub_url not configured)`.
- `hub_secret` must match the server's `PICO_ANNOUNCE_SECRET` env var. Sent as `X-Pico-Secret` header on every announcement POST.
- There is **no announce timeout key** in `config.json` and adding one is not the fix for a slow hub: the announce budgets are firmware constants (see §Announce transport & watchdog budgets), deliberately not operator-tunable.
- `config.json` is gitignored — the local working copy holds the real credentials (untracked, not committed).
- `config_loader.py` provides defaults for all fields **except `hub_secret`** (which has no default — treated as optional `""` by the validator). Example defaults: device_name `"PicoDevice"`, period_s `10`.
- `networks` is optional. If present, `connect_wifi()` tries each in order; first success wins. The primary `ssid`/`password` pair is tried first.
- `pins` is a dict mapping device roles to GPIO pin numbers (`dht`, `humidifier`, `fan`, `heater`). Each value must be one of the assignable user GPIOs **1–22, 26, 27, 28** — GP0 is the force-provision jumper and GP23–25/GP29 are reserved for the CYW43439 wireless chip (reserved-GPIO constants live in `app/config_validator.py`, see §Unit page) — and every role needs a **distinct** GPIO — a collision is a fatal boot error, including one created by a partial `pins` object colliding with a default left in place (e.g. `{"pins":{"humidifier":4}}` duplicates the default `dht: 4`). Correction means uploading a corrected `config.json`. Persisted by `POST /setup`; falls back to defaults if missing.
- `active_high` is a boolean controlling relay polarity (`false` = active-low, the safe default for common relay modules). Persisted by `POST /setup`; falls back to `false` if missing.
- `reboot` controls the daily scheduled soft-reboot + NTP sync (`enabled`, `hour`, `minute`, `ntp_host`, `ntp_tz_offset_hours`). Disabled by default (`enabled: false`). `hour`/`minute` are matched against the unit's **local** clock (`UTC + ntp_tz_offset_hours`), and no API writes these keys — the change path is edit `config.json` + reboot (see the time-semantics bullets in §MicroPython quirks).
- `control.hyst_temp` is **deprecated / vestigial** — `app/control.py` never reads it (heater control uses `temperature_deadband`). It is still present in the defaults (`config_loader.py`) and validated by `config_validator.py` (int, 0–50), so it is accepted and persisted, but has no effect.

## LED Status Indicators

- **OFF**: boot-time Wi-Fi attempts only — `connect_wifi()` keeps the LED off between retries while it works through the candidate list (check SSID/password on the console). It is **not** the *runtime* link-down state any more: `wifi_watchdog_loop()` now shows the **offline double-blink** while it retries reconnection (`app/wifi.py`, see §Wi-Fi watchdog).
- **SOLID**: Wi-Fi connected, but the hub announcement is pending or not yet acknowledged — `announce_then_retry_once()` lights it when the boot attempt starts and only replaces it on an ack, so a connected unit that is never acknowledged stays solid (this is also where standalone running lives: with `hub_url` empty the announce task keeps retrying a skipped attempt and the LED never leaves solid).
- **HEARTBEAT** (even blink): acknowledged by the Mushroom Pi hub — healthy operation **within a hub**. It is not generic "normal operation": an unacknowledged unit never leaves SOLID.
- **Note on link recovery**: the link-down blink replaces the heartbeat, and link-up **re-arms it directly** — `wifi_watchdog_loop` calls `io.start_led_heartbeat(period_ms=800, stop_event=...)` after a successful reconnect (the helper cancels any existing blink/heartbeat task first, so it cannot double-start; only the link-down blink can be live at that point). A recovered link therefore shows the heartbeat again for an acknowledged unit without needing another announcement. Because wifi.py holds no announce-ack state, the re-arm is unconditional: an *unacknowledged* unit also blinks once its link is back, so after a link cycle the heartbeat means "Wi-Fi recovered"; it stops meaning "the hub accepted" until a pending announce attempt settles the LED again (see §Wi-Fi watchdog).
- **SLOW DOUBLE-BLINK** (offline / working): 200ms on / 200ms off / 200ms on / 800ms off — the unit is **working** (regulating, serving its page) but has **no usable Wi-Fi link**: no network configured, a failed join, a force-provision boot, or a runtime link drop (during which it brings its own AP back up). It is not a fault and not a provisioning-only state — control continues throughout. Shown whenever its own AP is offered: from boot in the offline (AP) operating mode (§Offline (AP) operating mode) and during a runtime link-drop (§Wi-Fi watchdog).
- **CONFIG ERROR** (3 fast blinks): 150ms on / 150ms off × 3, 1000ms pause, repeating — `config.json` is malformed, has invalid values, or assigns the same GPIO to two device roles; check serial console for details (duplicates name the colliding GPIO and both `pins.<role>` names). Terminal state — the device does not start any services.
- **Note on PIN remaps**: `IO.remap()` re-runs `IO.__init__()`, which resets `_hb_task`/`_hb_enabled` — the live heartbeat or double-blink task exits on its next iteration and its `finally` turns the LED off. `POST /setup` therefore re-arms the mode-appropriate indicator right after remapping: `io.start_provisioning_blink(stop_event=...)` (the offline double-blink) when the unit has no link, `io.start_led_heartbeat(period_ms=800, stop_event=...)` on STA — the same pattern as the announce-ack and link-recovery arms. The STA re-arm is unconditional (`api.py` holds no announce-ack state), so, exactly like the link-recovery re-arm above, a not-yet-acknowledged unit starts blinking again after a remap until a pending announce settles the LED.

## Coding Rules (Gotchas)

### Version constants (`app/state.py`)

- **`_SOFTWARE_VERSION`** is the firmware version's single source of truth (`GET /system`, `GET /`). Bump it only on release (`main`), never during `dev`; every bump keeps `spec/openapi.yaml` `info.version` and `mushpi-mock` in sync.
- **`_API_VERSION`** (same file) is the Pico↔Server contract generation — bump only on breaking changes. Any `dev` bump needs a matching ≥ MINOR `_SOFTWARE_VERSION` bump.

### RAM budget

~520 KB on RP2350 (Pico 2 W); avoid large imports, f-strings, or unnecessary allocations. Call `gc.collect()` at the control-loop iteration boundary (after `evaluate_hysteresis()`, before the chunked-sleep loop) and in the HTTP `after_request` hook (`_cors()`). Per-call overhead is ~1–3ms — acceptable on a 10s+ loop and infrequent HTTP requests. This prevents heap fragmentation from accumulating over weeks of uptime.

### MicroPython quirks

- **No type hints**: MicroPython support is limited and CPython type annotations are stripped before upload.
- `urequests` does not support the `json=` kwarg — pass pre-serialised `ujson.dumps(body)` as `data=` with explicit `Content-Type: application/json` header. (Legacy guidance: the firmware no longer uses `urequests`, but `app/announce.py` still pre-serialises the body for the same reason — the hand-rolled transport writes `Content-Length` itself.)
- `usocket.setdefaulttimeout()` **does not exist** in this MicroPython build. The announce code used to call it behind a bare `except: pass`, so the failure was silent and the intended per-request timeout never reached a socket. Per-socket `s.settimeout()` is the only timeout control available — do not reintroduce a `setdefaulttimeout` call or a parameter that implies the timeout is configurable.
- **Announce no longer uses `urequests` at all.** `_post_once_async()` builds the request and the socket itself on `usocket`, because the library's behaviour was never dependable from this repo: `lib/urequests.py` is **gitignored**, so every flashed unit carries whatever copy someone uploaded, unversioned and unreconcilable. Its local `timeout=` parameter was **dead code** (`URLOpener` ignores the argument and calls `s.settimeout(5)` itself), and that hardcoded 5 s bounded only two of the three blocking phases — `socket.getaddrinfo()` had **no** timeout and the client's `while 1: s.recv(...)` loop granted **each round a fresh full timeout**, so the worst case was unbounded while `control_loop` held the watchdog's only feed site.
- DHT11 can return implausible readings; `DHTReader.plausible()` validates `-10 ≤ t ≤ 60` and `0 ≤ h ≤ 100`. **Garbage sensor readings must never leak into `status`**: `DHTReader.read()` writes `status["temperature"]` and `status["humidity"]` ONLY after `plausible()` returns `True`. Implausible readings set `last_sensor_error` but leave the last plausible values in place — **so the control loop keeps evaluating against a stale reading while the sensor is faulted**. The `None` guards only suppress actuation *before the first* plausible read. This is **not** fail-safe: from the loop's point of view a faulted sensor is indistinguishable from a working one, so a fault that persists can hold an actuator on a stale reading.
- **Sentinel-based reboot classification**: `machine.reset_cause()` on rp2 is unreliable for distinguishing intentional from watchdog reboots (both `machine.reset()` and `machine.soft_reset()` may report as `WDT_RESET`). Instead, **all intentional reboots** (scheduled, `POST /reboot`) write a `pending_type` sentinel to `uptime.json` via `mark_pending_reboot()` before resetting. `init_uptime()` reads the sentinel first; `reset_cause()` is used only as a fallback for unexpected reboots.
- **No battery-backed RTC — and the clock it does have holds *local* civil time.** `ntptime.settime()` sets the RTC to UTC; `sync_ntp_once()` (`app/reboot_scheduler.py`) then folds `reboot.ntp_tz_offset_hours` into the hour **before** rewriting `machine.RTC()`, so `time.localtime()` returns `UTC + offset` directly, no conversion at read time. Watch the tuple order: `time.localtime()` is `(y, mo, d, hr, mi, sec, wd, yday)` while `machine.RTC().datetime()` is `(y, mo, d, wd, hr, mi, sec, subsec)` — not interchangeable.
  - **`reboot.hour` / `reboot.minute` are compared against that local value** — `reboot_scheduler_loop()` matches `time.localtime()[3]`/`[4]` to the configured hour and minute. With `ntp_tz_offset_hours: 0` (the `config_loader.py` default) the configured hour is therefore a **UTC** hour. Reverse direction: `reboot_utc_hour = (configured_hour − ntp_tz_offset_hours) mod 24`.
  - **Whole hours only.** The offset is an integer validated to **−12…+14** by `config_validator.py`, so half-hour zones cannot be expressed.
  - **No daylight-saving handling anywhere.** The offset is a fixed integer the operator must change by hand when their zone shifts.
  - **Changing the offset requires a reboot**: `reboot_scheduler_loop()` reads it once when the scheduler task starts (`tz_offset = reboot_cfg.get(...)` before the loop), not per iteration — and `cfg` itself is loaded once at boot.
  - **The armed schedule is gated on a landed sync.** Time checks run only when `synced` is true, so with no sync landed no date is observed and no reboot can be armed: an unreachable or unresolvable `ntp_host` means *no scheduled reboot*, not a wrong one. (A failed `time.localtime()` read also clears `synced` and forces a re-sync.)
  - **No boot grace period exists** — `_NTP_RETRY_MS` is retry cadence, not a floor. Once a sync lands, the first 60 s poll matching `hour:minute` on a day not yet stamped reboots, even shortly after boot. The only guards are the sync gate above and the once-per-day stamp (`mark_pending_reboot("scheduled")` writes `reboot_done_date` to `uptime.json`).
  - **Reading the unit's clock on the bench:** the REST API exposes no timestamp, date, or timezone — only durations (`uptime_s`, `total_s`, `since_boot_s`). Use the MicroPico console: `import time; print("%04d-%02d-%02d %02d:%02d:%02d" % time.localtime()[:6])` — the same source the scheduler compares against (`uptime.today_str()` reads `time.localtime()` too).

### Announce transport & watchdog budgets (`app/announce.py`, `main.py`)

- **The rp2 hardware WDT tops out at ~8.388 s and `machine.WDT` cannot be stopped once armed.** So raising the timeout is **never** a mitigation for a long blocking operation: the window cannot go past the hardware ceiling, and an armed watchdog cannot be stood down while a slow call runs. The only available lever is making the blocking operation cooperative — which is what the announce budgets do. Do not "fix" a watchdog reset by lengthening `WDT(timeout=...)`.
- **For new code**: no single uninterrupted blocking operation may approach the ~8 s window — slice any new socket call, blocking driver or library with `await asyncio.sleep_ms()`, and never let a name lookup run while the watchdog is armed.
- **Why every announce phase is bounded and sliced** (the one-feed-site rule itself is core-tier, stated in `AGENTS.md`): because `control_loop`'s 200 ms chunked-sleep loop is the only thing that keeps the watchdog alive, any *other* task that blocks without yielding starves the feed for as long as it blocks. The announce transport therefore bounds every phase and puts an `await asyncio.sleep_ms(0)` at every phase boundary, so a slow or dead hub costs an announce, never regulation. The arithmetic: the largest single uninterrupted blocking stretch inside an attempt is one `connect()` bounded by `_CONN_TIMEOUT_S` (3 s of the 8 s window); every send/recv slice is bounded by `_IO_SLICE_S` (1 s) with an await between slices, and the header read is capped in *slice count* by `_RESP_BUDGET_MS`. Corollary for anyone adding an async task: your task is the thing that can reset the unit, and there is no second feeder to save it. Never add a feed site elsewhere — the design intent is that a dead `control_loop` stops being fed.
- **`ntptime.settime()` performs the same unbounded name lookup (`getaddrinfo`) inside the armed window** when `reboot.enabled` is true (default `False`) — `app/reboot_scheduler.py` runs it from the scheduler **task**, which is created after the `WDT` exists, so this resolution is *not* covered by the boot-path exception: the boot slot only ever holds the hub lookup. **Known, not fixed here**, and tracked separately: with scheduled reboots disabled the unit does not hit it, and a DNS answer for the NTP pool is normally fast, but the exposure is real and identical in kind to the one the announce transport was fixed for. If you touch the NTP path, this is the thing to revisit.
- **`ussl`-wrapped sockets may not expose `settimeout()`.** `_set_timeout()` therefore applies the timeout to the **wrapper and the raw socket** and treats either landing as success. If the wrapper silently ignores it, the https path's per-slice IO timeout degrades from 1 s to the 3 s connect timeout — still bounded, just coarser. The whole `https` branch is untested on hardware; assume it needs a bench pass before relying on it.
- **Boot-only resolution — the retry path never resolves.** `socket.getaddrinfo()` has no timeout of its own, so the hub name is resolved exactly once: `presolve_boot_hub()` at `main.py` module scope, after `connect_wifi()` returns and **before the `WDT` object is constructed** (the sanctioned blocking boot slot — this extends the existing "main.py boot path" exception in `AGENTS.md`; it must stay outside `main()`, and moving it into a task would put unbounded blocking back inside the loop). Runtime attempts use only the cached `_hub["addr"]`, or an IPv4 literal parsed straight from the config. Consequence, by design: a hub address change, or a boot lookup that failed, is picked up only at the **next boot**; with no usable cached address the attempt logs `no hub address available` and fails without any lookup, and the task keeps backing off. Adding a lookup to the retry path "just in case" is the bug this rule exists to prevent. There is deliberately **no TTL and no background re-resolve** — do not add either as a side effect.
- **The request line stays `HTTP/1.0` and the `Host:` header carries no port**, purely for wire compatibility with what the old `urequests` client sent the hub. Modernising either one (`HTTP/1.1`, `Host: name:port`) is a hub-side contract change: check the server's body-parser and the mock before touching it. `Content-Length` is written **exactly once** by the firmware — the old `urequests` header dict deliberately omitted it because the client appended its own copy, and a duplicate is what the old code comment warned would make the hub's body-parser reject the payload.
- **The retry schedule is forever, with backoff.** After a failed attempt, `announce_then_retry_once()` waits per `_RETRY_BACKOFF_S = (30, 30, 60, 120, 300)` seconds and retries — after the tuple is exhausted it repeats the last entry (300 s cap) until an attempt succeeds or the unit shuts down. `main.py` is the **only** spawner: the Wi-Fi watchdog no longer re-announces on link-up (see §Wi-Fi watchdog). The waits are pure `await asyncio.sleep()` — they hold nothing, so no interval, however long, can starve the watchdog; what keeps the armed window safe is the per-phase bounding above plus boot-only resolution.

### Wi-Fi watchdog (`app/wifi.py`)

- `connect_wifi()` is boot-only — it must **never** be called from a running task; runtime reconnect is `reconnect_once_async()`.
- `wifi_watchdog_loop()` polls the link every 5 s. On drop it brings the offline AP up (`ensure_ap_up(cfg)`) and swaps the heartbeat for the offline double-blink (`io.start_provisioning_blink(stop_event=...)` — the helper cancels the heartbeat task first; it replaces the old `io.led_solid(False)` force-clear, so a link outage now reads as the offline *blink*, not OFF), then retries `reconnect_once_async()` with backoff `_BACKOFF_MS = [5000, 10000, 30000, 60000]` (5/10/30/60 s, capped at 60 s thereafter until it connects). Regulation continues through the outage — `control_loop()` never inspects the link.
- **AP lifecycle idempotence**: `ensure_ap_up(cfg)` / `ap_down()` track the interface in the module-level `_ap_if`. The guard exists because `ap_setup_ssid()` momentarily toggles the AP (`active(True)` → read MAC → `active(False)`) to derive the SSID — re-running the sequence against a live interface would **flap it** and drop attached clients. `start_ap_provisioning()` (boot) is a thin wrapper over `ensure_ap_up()`, so boot and runtime share one AP-setup code path. On link-**up** the watchdog calls `ap_down()` before re-arming the heartbeat. Note for anyone extending wifi.py: the interface-config calls are synchronous (the established pattern — `reconnect_once_async()` likewise calls `wlan.active(True)` from inside the loop; only the connect polling stays async). The runtime AP bring-up is a blocking call inside the armed WDT window — bounded in practice by the CYW43 AP start, and a deliberate, bench-flagged exposure.
- On link-**up** it first drops the outage AP (`ap_down()`), then refreshes the cached WLAN info (`attach_wlan_info(wlan, cfg)`), reads the new IP, re-arms the LED heartbeat (`io.start_led_heartbeat(period_ms=800, stop_event=stop_event)` — the helper is cancel-first, so it cannot double-start, and it is a cold start here because the link-down blink already replaced any heartbeat), and logs. There is **no hub-cache invalidation** (no runtime lookup exists to be invalidated — see §Announce transport & watchdog budgets) and **no announce respawn**. What covers the respawn's old jobs: if the boot announce is still unacknowledged, its task is still running its backoff loop and the first attempt after link-up carries the new IP (the payload reads the same `state` cache `attach_wlan_info()` refreshed); if the boot announce already succeeded, that task has *returned* and nothing re-announces this boot — the hub's 60 s poll refreshes the unit's stored IP over `GET /` independently of any announce. The heartbeat re-arm replaced the respawn's other former job (re-lighting the LED after a link bounce); it is unconditional because wifi.py holds no announce-ack state — see the §LED Status Indicators note. Do not reintroduce a respawn for LED purposes or otherwise (it created two forever-retrying announce tasks).
- **Module-ownership**: announcing is entirely `app/announce.py`'s concern, and `main.py` is its only spawner — `wifi.py` no longer imports `announce` at all. The removed link-up respawn is deliberate, not an oversight: with the boot task retrying forever, respawning created two forever-retrying announce tasks (doubled attempt logs, a possible double heartbeat) and bought nothing. Do not reintroduce a runtime re-announce without first solving that overlap — and note the link-up moment was also the only place a runtime lookup could once happen; boot-only resolution closed that too.

### Persistence

- **`uptime.json`** is a runtime-persisted file at flash root (like `config.json`). Created by `init_uptime()` on every boot. Schema: `{"cumulative_ms": int, "reboot_done_date": "YYYY-MM-DD" | null, "pending_type": "scheduled" | "soft" | "hard" | null}` — `pending_type` is the reboot-classification sentinel written by `mark_pending_reboot()` and cleared to `null` by `init_uptime()` on the next boot. Device-local only — never sent to the hub. Atomic write via `.tmp` + `os.rename`.
- **`reboot_reason` enum**: the valid values produced by `app/uptime.py` are `scheduled`, `soft`, `hard`, `watchdog`, `power_on`, `unknown`. Document these in the `uptime` response schemas and keep `spec/openapi.yaml` in sync.
- **Uptime in `GET /health`**: the value appears twice — the scalar `uptime_s` (cumulative seconds) and the `uptime` object (`total_s`, `since_boot_s`, `reboot_reason`, `scheduled_reboot`).
- **Persist config** with `save_config(cfg)` — atomic write via `config.json.tmp` + `os.rename`. Never `open('config.json','w')` directly.
- **`POST /provision` `wifi` key** persists to flash. **`POST /setup`** also persists `pins` and `active_high` to flash (survives reboot). Setpoints, the control-loop flag, and the hand-set fan/humidifier positions persist to **`runtime.json`** (see the next bullet) — no longer runtime-only.
- **`runtime.json`** is a runtime-persisted file at flash root (like `uptime.json`), written by `app/runtime_state.py`. Schema: `{"version": 1, "setpoints": {"temperature": int, "humidity": int}, "control_enabled": bool, "outputs": {"fan": bool, "humidifier": bool}}`. **There is deliberately no `heater` key** — the heater is never persisted and always restored OFF. Atomic write via `.tmp` + `os.rename`. Device-local only — never sent to the hub. Only the three POST handlers in `api.py` write it (grower intent); the control loop and sensor path never touch flash. **`restore()` behaves identically in STA and offline boots** — the former AP skip (setpoints/flag only, relays untouched because the offline loop did not run) is removed: a loop-off boot re-drives the persisted hand-set fan/humidifier positions on either network, because the offline mode runs the control loop too (heater still never restored ON). `restore()` clamps setpoints at **load** to the unit-page slider ranges (temperature 0–50, humidity 10–90) and drops wrong-typed fields per-field, so a damaged file degrades to defaults instead of refusing to boot — this is defensive restore-clamping only; `POST /setpoints` itself still does no range validation. **Deliberately NOT `config.json` — do not unify the two:** `config.json` is the operator-flashed provisioning artifact (gitignored, uploaded by MicroPico, rewritten wholesale by `save_config()`); persisting grower state there would wipe the grower's targets on every re-deploy and rewrite Wi-Fi credentials and `hub_secret` on every target tweak.
- **Flash-fault asymmetry**: `uptime.py`'s `_atomic_write()` swallows failures (best-effort bookkeeping); `runtime_state._atomic_write()` **propagates** and each POST handler wraps the call in `try/except` + `print` — a failed flash write is logged on serial but must not fail the request (the response stays 200 with the live state). Do not "harmonise" the two by silencing runtime_state's writers — the handlers' guards depend on propagation.

### Shared-state pitfalls

- **Exact key names**: the `status` keys (`fan`, `humidifier`, `heater`) must match `devices["pins"]` and the JSON names in `GET /` (`outputs.*`) and `GET /outputs`. A key typo (`heat` vs `heater`) silently desyncs: the GPIO toggles but `status` stays stale, so the server always polls `false`.
- **Manual-override writer**: `POST /outputs` (`_setoutputs` in `app/api.py`) is the one sanctioned exception to the IO-helpers-only rule — it writes GPIO via `io.write(pin, bool)`, then sets `status[...]` and the min-runtime markers itself. Any other code writing these keys is a bug.
- **`POST /setup` GPIO writer the rule does not name**: `io.remap()` → `IO.__init__()` re-initialises every relay to its off level directly (not through the helpers) and never touches `status` or `_on_since` — after a remap the cached relay state and min-runtime markers go stale (`GET /outputs` may report a pre-remap value) until the next `control_loop()` tick reconciles through the helpers. Sanctioned exception to the IO-helpers-only discipline (the core `AGENTS.md` names only `POST /outputs`): the endpoint re-points which pins the helpers drive rather than driving them — do not "fix" it by writing `status`/`_on_since` from the handler.
- **Boot restore is sanctioned too**: `runtime_state.restore()` at boot drives relays **only through the `IO` helpers**, so it is not a direct `status` writer.
- The `status` relay keys are the single source of truth for API relay state — there is deliberately no GPIO read-back.
- **Import-time snapshots**: `status` must be read live inside handlers — a snapshot copied into a module-level dict at import time captures initial values and never updates.

### Graceful shutdown (`app/shutdown.py`)

- `main.py`'s `finally` calls `graceful_shutdown()`, which turns all outputs off and disconnects WiFi; its `sensor` parameter is accepted but unused — the sensor is not deinit'd.

## REST API notes

### Unit page (`app/unit.html`, `GET /ui`)

- **What it is.** The unit serves its own self-documenting status-and-control page as the landing page in every mode: `GET /` for HTML browsers, with `GET /ui` kept as a stable alias (always text/html in both modes; offline (AP) = the same page with an offline banner whose "To join a network" link points at the Wi-Fi setup form, `GET /provision` — **fully operable, PIN mapping included**, since the control loop runs offline; see §Offline (AP) operating mode). `app/api.py` reads `app/unit.html` once at import into `_UNIT_HTML` (OSError fallback to an error stub — same pattern as `provision.html`) and injects the `MODE` (`"sta"`/`"ap"`) and `DEVNAME` placeholders. The page is hand-authored HTML + inline CSS + vanilla JS: no build step, no CDN — it must work offline on the unit's own network.
- **Placeholder injection is load-bearing.** `_UNIT_HTML.replace("MODE", mode).replace("DEVNAME", name)` — MODE first, so a `device_name` containing the literal token can never be re-scanned. The tokens now live in the page's inline bootstrap — `window.__UNIT__ = {mode:"MODE", name:"DEVNAME"};` — and `app/static/unit.js` binds `unitMode`/`devName` from it; the bootstrap property names are deliberately **lowercase** because an uppercase property would add a second occurrence of the token on the same line. Each token must still occur **exactly once** in `app/unit.html` (the mixed-case `unitMode`/`devName` identifiers keep surrounding code free of the tokens); the asset is **never** string-replaced, so it must hold **zero** occurrences — a stray token would ship to the browser literally. Case-sensitive grep check: `MODE` → 1 and `DEVNAME` → 1 in `app/unit.html`; both → 0 in `app/static/unit.js`. The head of both pages carries no token by design: the `<title>` is static brand text (`Mushroom Pi · …`) and the icon link is static, so the device name stays only in the header card — a token there would add a second occurrence and break the exactly-once invariant. Known hazard, unchanged by the move: a `device_name` containing `"` or `\` breaks the bootstrap JS literal — pre-existing (it equally corrupted the old `var devName = "DEVNAME";` form), no regression, no hardening.
- **`GET /` content negotiation** (now in both modes) is a strict predicate, not the usual "html beats */*" heuristic: `'text/html' in accept and 'application/json' not in accept` → the unit page; **everything else → JSON**. The hub's axios poll sends `Accept: application/json, text/plain, */*` and must keep getting JSON — any Accept mentioning `application/json` gets JSON. Microdot's `Headers` lookup is case-insensitive, so the header name's case is free. The page's own STA fetch pins `Accept: application/json` explicitly; offline it still composes the same view from `GET /system /health /sensors /outputs /setpoints /control /setup` — the loader is deliberately unchanged (the offline composition predates the unified landing page and works identically).
- **Hub state (`state.hub`).** `hub = {"configured": bool, "connected": bool}`, mutated in place; the **only writer is `app/announce.py`**: `announce_then_retry_once()` sets `configured` from `cfg["hub_url"]` and clears `connected` at loop start, clears `connected` after every failed attempt, sets it on a 2xx ack. `GET /` exposes `hub.configured` read live from `cfg` and `hub.connected` from the dict. Semantics: "connected" means the hub acknowledged the **most recent announce** (boot/reboot) — the unit never pings the hub between announcements, so this does **not** detect a hub outage; the hub's ~60 s poll holds its own view. The page's Hub card must keep that wording honest.
- **RAM budget (mechanism).** One page load is now **three** dispatched requests: the HTML (`/ui` or the negotiated `/`), `GET /static/unit.js`, then the page's own JSON fetches. The JS no longer sits in the page string — `send_file` streams `app/static/unit.js` from flash in 1 KB chunks — so `_UNIT_HTML` is ~24 KB on the heap for the whole session instead of ~47 KB (file sizes: `app/unit.html` 47,542 → 23,930 B; `app/static/unit.js` 23,708 B), and every page request still runs two `.replace()` passes over that ~24 KB string, reclaimed by the `after_request` `gc.collect()`. Because one load is three requests, `_cors()`'s `gc.collect()` now runs 3× per page load; the browser's `favicon.svg` icon fetch rides alongside as a further small streamed request (no heap string). Before/after **heap** figures remain unmeasured on the prototype unit — they belong on the issue, not here (hand-off item).
- **Static asset mechanics.** `GET /static/<string:filename>` (`_static` in `app/api.py`) serves the page's static assets through the vendored Microdot's `send_file`: `unit.js` as `application/javascript` and `favicon.svg` as `image/svg+xml` — the favicon's `rel=icon` link is shared by `unit.html` and `provision.html`. `content_type` is passed **explicitly** from `_STATIC_CONTENT_TYPES` (a module-level extension→type map; unknown extensions stream as `application/octet-stream`) so the firmware does not depend on the gitignored vendored library's inference. The response is **HTTP/1.0** and carries **no `Content-Length`** for file bodies (`Response.complete()` sets it only for `bytes` bodies). This Microdot has **no ETag / `If-None-Match` / `304`** support, so a browser holding a copy cannot cheaply revalidate — hence `max_age=0`: every page load re-fetches the asset (a full re-download over the unit's own link, cheap) and a reflash is picked up on the next load instead of the browser serving the previous firmware's JS for an hour. `send_file` opens the file **inside** the handler, so the route wraps the call in `except OSError` → 404 `{"ok": False, "error": "static asset missing"}` (mirroring the `_PROVISIONING_HTML`/`_UNIT_HTML` stubs) — the body string changed from `"unit page asset missing"` when the single-purpose `_unit_js` route generalized to any asset, and `spec/openapi.yaml` quotes the new string. `.py` and `.js` upload separately, and without the guard a unit missing an asset would 500 while the page silently rendered with no controls. **Any future static asset needs the same guard.** The assets are page surface only — hub and server never consume them.
- **Asset extensions gate deployment.** A file's extension must appear in `micropico.syncFileTypes` (`.vscode/settings.json`) or MicroPico **silently never uploads it** — the request then falls to the missing-asset guard. `svg` had to be added there for `favicon.svg`; any future asset type needs the same addition.
- **Segment type: `string`, not `path`.** `<string:filename>` compiles to `/([^/]+)` (the vendored Microdot's built-in `URLPattern.segment_patterns`) — a single path component, no slashes — so a path-traversal shape can never reach `send_file`; `<path:filename>` would match `/static/../../x` and hand the constructed path to the filesystem. A detail of the gitignored vendored library, recorded because the route's safety rests on it.
- **Do not trim assets for size.** Static files live in flash and stream through `send_file`'s 1 KB buffer, so their byte count never enters RAM. `app/static/favicon.svg` is a byte-for-byte copy of `mushpi-client/public/favicon.svg` (2,630 B, Inkscape metadata intact): trimming it buys no RAM and would only diverge from the client's original.
- **Reserved-GPIO constants** live in **`app/config_validator.py`** (canonical; firmware constants, deliberately NOT `config.json` keys): `VALID_USER_GPIO` (1–22, 26, 27, 28), `RESERVED_GPIO_REASONS` (GP0 = force-provision jumper sampled at boot; GP23–25 and GP29 = CYW43439 wireless chip), `VALID_GPIO_HINT`, `gpio_reject_reason(v)`. `app/api.py` imports them for `POST /setup`, so boot validation (`validate_config()`) and the live endpoint refuse the exact same set with the same named reasons from one source (the plan named `api.py` as the home; the shared-import placement is the accepted deviation). The merged-view duplicate-GPIO rule set is **separate and untouched** by this range — see the root contract notes.

- **Mock mirror (vendored copy).** `mushpi-mock` serves a **checked vendored copy** of this page and its assets, kept byte-identical to `app/unit.html`, `app/static/unit.js` and `app/static/favicon.svg`; the mock-only differences (the "simulated" labels, the restart disclosure) are applied at render time inside the mock, never in the vendored bytes. **Consequence: a change to the page or its JS must always be propagated to the mock** — including pure wording, CSS or layout edits that alter no endpoint, because the mock's copy is compared byte-for-byte and its drift check fails on any difference. The mock owns the refresh and the check (`mushpi-mock/scripts/refresh-unit-page.sh`, `mushpi-mock/scripts/check-unit-page-drift.sh`); the grow-side duty is to flag the change as **mock impact** in the plan and in the builder's report.

### CORS preflight

- `app.options_handler` (`app/api.py`) answers `OPTIONS` on any path with a **per-path `Allow`** header and a fixed `Access-Control-Allow-Methods: GET, POST, PUT, OPTIONS`. `HEAD` is answered implicitly by the GET routes (and listed in `Allow` whenever `GET` is).
- Preflight is **deliberately absent from `spec/openapi.yaml`** — it is not contract, so there is no mock sync duty; `mushpi-mock` answers preflight with FastAPI's CORS middleware.
